## Notes

**§1 Tags and digests.** Deploy already pins by digest by default (`deploy.go:155`, `--no-digest` is the escape hatch), and build state is per worktree and per env under `.forge/state/`. So a dev-only scheme of **one moving tag per worktree** (`<image>:wt-<worktree>`) plus a digest pin in the manifest is safe for rollout correctness and bounds tag growth. Superseded manifests become untagged, so the registry also needs delete enabled and an offline `garbage-collect`. Release envs should keep `git describe` tags for provenance.

**§2 k3s args.** `spliceK3dCIDRs` (`dev_cluster_ingress.go:418-473`) merges `{arg, nodeFilters}` entries into `options.k3s.extraArgs` and refuses conflicts. A sibling `spliceK3dKubeletGC` is the obvious seam. Because kubelet thresholds are percentages and Docker's disk is a 1 TiB sparse file, also ship a byte-capped node-image pruner (`docker exec <node> crictl rmi --prune`, which removes images that no container uses).

**§4 Prune.** `devstack.Prune` is correct and conservative (git `worktree list --porcelain` liveness; it never touches standalone keys or block 0), but it is manual and limited to port blocks.

**§8 Existing reclaim and diagnostics surface:**

- `forge env devstack prune [--dry-run]` reclaims port blocks for gone worktrees.
- `forge doctor`:
  - `CheckDocker` (`internal/doctor/docker.go:72`) checks reachability and the compose services. It reports no disk usage.
  - `CheckOrphanedClusterObjects` (`orphanedcluster.go:191`) only reports.
- pgtest `reapStaleInstances` runs automatically at boot.

There is no `forge gc`, `forge clean` or `forge prune` for images, registries, volumes, tmp or caches.

**§9 control-plane `scripts/registry-retention.py` (candidate spec):**

- **Policy** (`deploy/registry-retention.json`):
  - container, docker context
  - `retain_days: 14`, `keep_versions: 5`
  - an allowlist of repositories
  - `protected_tags` (latest/dev/e2e/main/stable)
  - registry aliases, so that `localhost:5051/x` and `k3d-…:5000/x` count as the same repo
  - kube contexts
- **Protection:** every image referenced by pods, controller pod templates (including old ReplicaSets) and resolved pod imageIDs, in every listed context, plus containers. References are normalised through the aliases.
- **Selection, per repo:** keep the newest N by push time, keep anything newer than the TTL, keep protected tags, and keep protected digests. DELETE is by digest, so one protected alias protects every tag sharing that digest.
- **Apply:**
  1. Verify cluster access before interrupting anything.
  2. Delete manifests through the API, with a helper registry that has delete enabled.
  3. Stop the registry.
  4. Run `registry garbage-collect` in a maintenance container with `--volumes-from`.
  5. Restart the registry. It refuses to restart over a maintenance writer that is still running.
- Dry run is the default. It installs itself as a launchd job.
- In forge this maps onto a `forge.Registry.retention` KCL block plus an automatic step after `forge env deploy`/`up`, since forge already knows the contexts, aliases and live digests.

## Top 5 forge defects by GB impact

1. **No registry retention, and the forge-created registry has delete disabled.** This accounts for ~55G (registry volume). Unique tag per commit or dirty build, `k3dRegistryCreate` passes no `REGISTRY_STORAGE_DELETE_ENABLED`, and there is no GC.
2. **No node image GC on forge-created k3d clusters.** ~40G (two node containerd stores). `spliceK3dCIDRs` projects only the CIDRs; there are no kubelet GC args and no byte-cap pruner.
3. **Test-suite tmp leaks around forge's cgo link and build steps.** ~15G of `go-link-*` (linker temp dirs from killed or timed-out builds spawned by forge's e2e and tierguard suites), plus 3.9G of `tierguard-*`. There is no sweep.
4. **Test fixtures that never clean up.** ~0.75G per accumulation and growing: `forge-e2e-bin-*` (526M), `forge-skill-validate-*` (160M), `forge-kcl-module-test-*` (66M), `embedded_postgres_log*` (an upstream leak not compensated in pgtest). A TestMain `RemoveAll` would fix each one.
5. **No worktree-death or compose-volume sweep.** ~7G of dangling `<project>_{postgres_data,go_build_cache,go_mod_cache,lgtm_data}` volumes from the scaffold compose template, plus per-worktree node_modules. `devstack.Prune` covers only port blocks, and no doctor check reports dangling compose volumes. (Unbounded `.forge/logs` growth during a long `up` is a smaller sixth.)
