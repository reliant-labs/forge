# Mobile foundation dependency/runtime compatibility audit

## Scope and verdict

Audited repository HEAD `6c04734393bf58a20adfe169f1904b29009206f2`; registry/docs queried during this audit (2026-11-07). Research only: no implementation, dependency installation, native build, or device execution. Existing `mobile-release-target.md` is an architecture proposal, **not implementation evidence**. Line references below are to this HEAD.

**No: the mobile scaffold is not current, nor demonstrably production-compatible with the web foundation.** Its Expo 52 dependency family is largely internally coherent, but its runtime range cannot resolve from the public registry. Transport capability and authenticated native operation are not established by a shared interceptor API. React 18 versus web React 19 is not itself a defect: Expo owns the React/RN compatibility matrix.

Severity: **high** blocks install or essential authenticated operation; **medium** leaves an advertised capability incomplete or a fragile boundary; **low** cleanup/documentation. “Verified” means source/metadata evidence, not a device test.

### 1. HIGH — native runtime dependency cannot resolve (verified metadata defect)

`internal/templates/frontend/react-native/package.json.tmpl:21` requests `@reliantlabs/forge-web-runtime: ^0.2.0`. Registry metadata contains **no 0.2.x versions**; published versions begin at 0.3.0. Semver `^0.2.0` excludes 0.3 and 0.13. Web requests ^0.13.0; checkout is 0.13.3 (`web-runtime/package.json:3`). A normal registry-backed install cannot satisfy the native manifest. No installation was run; failure follows directly from range/registry evidence.

Local-runtime linking is not a published-consumer proof: `internal/cli/webruntime_prebuild_e2e_test.go:15-24` explicitly describes frontend e2e installing this checkout's runtime. Native Metro also explicitly accommodates the local bridge (`internal/templates/frontend/react-native/metro.config.js:28-35,78-90`). Test a registry-only released scaffold separately. Reported upstream as Forge bug `339531a4-f183-40f2-96cb-3a25910044e0`.

### 2. MEDIUM — Expo family is old, but not arbitrarily mismatched (verified)

SDK 52/RN 0.76 is not current relative to observed Expo latest 58. Do not independently upgrade React, RN, Router, safe-area, screens, and jest-expo to npm latest. Upgrade as a tested Expo matrix, with [Expo's upgrade procedure](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) and `expo install --check`/Expo Doctor validation in an isolated rendered project.

Router 4.0.22 [metadata](https://registry.npmjs.org/expo-router/4.0.22) depends on React Navigation native ^7.0.14, native-stack ^7.2.0 and bottom-tabs ^7.2.0. It peers on linking ~7.0.5, constants ~17.0.8, screens and safe-area. Drawer ^7.1.1 and reanimated are **optional peers**: their absence is not evidence that this simple Stack requires them. RN 0.76.9 [metadata](https://registry.npmjs.org/react-native/0.76.9) accepts React ^18.2, so scaffold React ^18.3 is peer-compatible; prefer Expo's exact recommended 18.3.1 for reproducibility.

The explicit `query-string` dependency (`package.json.tmpl:34`) and workspace-hoisting workaround (`metro.config.js:13-26,50-76`) should be re-evaluated against the chosen SDK/package manager rather than carried forever. SDK 52 [monorepo guidance](https://docs.expo.dev/guides/monorepos/) provides automatic Metro workspace configuration. The dev-runtime external symlink is a distinct requirement; deleting all custom Metro settings without testing would be unsafe.

### 3. MEDIUM — advertised Expo web path omits React DOM (verified omission; build untested)

Native manifest advertises `expo start --web` (`package.json.tmpl:11`), includes react-native-web (`:39`), and app config selects Metro/static web (`app.json.tmpl:20-23`), but declares no react-dom anywhere in that manifest. [Official SDK 52 Router installation](https://raw.githubusercontent.com/expo/expo/sdk-52/docs/pages/router/installation.mdx) requires both react-native-web **and react-dom** for web. Auto-installed transitive/peer packages or a workspace sibling are not a correct direct dependency declaration; an actual clean web export was not attempted.

The same official installation instructions confirm existing essentials are present: Router entry (`package.json.tmpl:6`), linking/constants/screens/safe-area/status-bar, app scheme (`app.json.tmpl:7`), Metro web bundler and `babel-preset-expo` (`babel.config.js:1-6`). Do **not** report gesture-handler or reanimated as universally missing requirements: this SDK's documented SDK-50+ basic installation does not require them. `expo-dev-client`, auth-session, web-browser and secure-store are not basic Router requirements either; they become requirements of chosen development/auth capabilities.

### 4. HIGH for streaming claims — native Fetch/Hermes compatibility is not proven

`react-native/src/lib/connect.ts.tmpl:47-51` supplies only baseUrl/interceptors to connect-web: no native fetch adapter, stream capability check, or global initialization. Official [Connect 2.0 transport source](https://raw.githubusercontent.com/connectrpc/connect-es/v2.0.0/packages/connect-web/src/connect-transport.ts) uses global fetch by default; unary JSON reads `response.json()`, binary reads `arrayBuffer()`, streaming reads `response.body` via a reader. Client/bidirectional request streaming is explicitly rejected. [Its initial assertion](https://raw.githubusercontent.com/connectrpc/connect-es/v2.0.0/packages/connect-web/src/assert-fetch-api.ts) only constructs Headers: successful transport construction proves very little.

[SDK 52 Expo fetch docs](https://raw.githubusercontent.com/expo/expo/sdk-52/docs/pages/versions/v52.0.0/sdk/expo.mdx) explicitly provide `expo/fetch` with streaming response readers. Scaffold does not select it. **Hypothesis requiring Hermes execution:** default RN fetch lacks the reader behavior needed for server streaming; unary calls may still work. A JS-only/polyfilled or browser test cannot certify native behavior. Connect ^2 can resolve later 2.x, so inspect the actual resolved transport in the validation fixture too.

Validate Headers, AbortController/timeouts, TextEncoder/TextDecoder, Uint8Array bodies, response readers/cancellation and UTF-8 fragmentation on supported Hermes versions. Do not assert Hermes supports all browser Fetch APIs merely because TypeScript accepts DOM types. `web-runtime/src/trace.ts:50-63` explicitly falls back from crypto.getRandomValues to Math.random; this avoids one missing-global crash but is neither credential-grade randomness nor proof that every runtime primitive exists.

### 5. MEDIUM — intended platform-neutral runtime boundary is bypassed (verified imports; crash untested)

Good existing seam: mobile Connect imports `/interceptors` (`connect.ts.tmpl:3,40-45`), whose implementation imports Connect/protobuf/OTel, errors, trace and telemetry gate (`web-runtime/src/interceptors.ts:35-46`). It exposes token/brand/error callbacks (`:53-64`) rather than importing app auth. Browser SDK is an optional peer, not inherently required by transport. Preserve this design.

But shared templates still import the full browser-oriented barrel:

- `internal/templates/frontend/shared/src/lib/query-client.ts:2`: value `userMessage`.
- `internal/templates/frontend/shared/src/hooks/use-optimistic-mutation.ts:1,5`: value `userMessage` and error type.
- `shared/src/hooks/{use-api-query,use-api-mutation,use-query-resource,use-join}.ts:3`: error type from barrel (type-only imports erase at runtime but still traverse declarations).

That barrel re-exports session/providers/error boundary/toasts/Resource and browser attribution (`web-runtime/src/index.ts:92-131,162-180`), while the runtime's own comment claims mobile avoids it (`interceptors.ts:3-12`). Existing React-18 peer support and dual typecheck (`web-runtime/package.json:68,83,110`) mean **do not repeat the stale assertion that current runtime categorically rejects React 18**. Nevertheless the import graph is broader than intended; Metro resolution/tree-shaking and DOM typings need separate checks. No actual Hermes import crash was reproduced.

### 6. HIGH production gap — native identity is a mock, not native authentication (verified)

`shared/src/lib/auth/context.tsx.tmpl:80-105,114-124,180-184` selects a fixture session provider for RN; `react-native/app/_layout.tsx.tmpl:8-22` explicitly does not wire a credential bridge. `react-native/src/lib/connect.ts.tmpl:21-30,43-45` defaults token getter to null. Consequently protected RPCs have no real bearer token even when mock UI identity appears signed in. This is honestly documented starter behavior, not an implemented native auth flow.

Web is materially different: Vite Connect uses an Unauthenticated callback and credentials-include fetch (`vite-spa/src/lib/connect.ts.tmpl:61-82,121-125`); mobile supplies no onError callback. Shared context subscribes to auth:expired (`shared/src/lib/auth/context.tsx.tmpl:162-178`), but mobile transport does not emit it. Wiring token attachment alone does not implement restore, refresh, expiry, logout/revocation, or query-cache identity isolation.

Implement native auth with a real public-client flow: system browser authorization-code + PKCE, registered native redirects, no embedded client secret, secure refresh-token storage, serialized refresh and explicit lifecycle state. Official references: [Expo authentication](https://docs.expo.dev/guides/authentication/), [AuthSession](https://docs.expo.dev/versions/latest/sdk/auth-session/), [SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/), [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252). Latest docs describe capabilities, not SDK-52 package pins. Choose dependencies with expo install for the selected SDK. The scaffold comment that RN has “no cookie jar” should not become a universal platform claim: native cookie behavior varies; what is established here is that the browser same-origin/session contract is not implemented and tested for native.

## Recommended boundaries and trade-offs (no implementation)

1. **First repair published dependency resolution.** Centralize compatible Forge runtime constraints across scaffolds; pin an explicit Expo dependency matrix and test rendered manifests against registry artifacts. A local bridge remains useful for development, but must not substitute for release-consumer testing.
2. **Prefer additive neutral subpaths before splitting packages.** Put error formatting/types, interceptors/trace, hooks contracts behind narrow platform-neutral exports; keep old barrel paths working throughout v1. Update all shared consumers, not only connect.ts. A separate runtime-core package gives stronger peer isolation but creates another release/version coordination boundary. An additive export is simpler if graph tests prove it truly neutral; do not just rename a barrel containing DOM components “core.”
3. **Separate common transport policy from platform network/session construction.** Share normalization, headers, trace and retry policy; let browser supply cookie fetch and native supply an Expo-compatible Fetch implementation and token accessor. Inject these into a factory rather than grow platform enums or a global singleton that owns auth. Trade-off: a small factory adds configuration, but makes mock transport tests and isolated app instances simpler. React Query should remain the one default retry owner (`interceptors.ts:24-34,184-199`).
4. **Keep navigation and identity acquisition platform-owned.** Shared API descriptors/hooks and identity read models are useful; browser route guards, cookie brokers, DOM telemetry and native secure storage/redirect handling are not interchangeable. Thin consumed token/expiry interfaces are preferable to one cross-platform provider full of platform branches. Do not migrate browser cookies into JS-readable tokens just to make the shapes identical.
5. **Upgrade Expo as its own deliberate change.** Compare maintaining SDK 52 (lower immediate migration effort, older ecosystem) with adopting the current verified stable SDK (migration work, new-architecture/navigation constraints). Prefer a current supported SDK after clean fixture validation, not blindly “latest” on every generated app. Keep SDK-specific Metro overrides only where evidence requires them; separate dev-link support from workspace policy.

## Validation handoff / uncertainty ledger

No package install, Expo Doctor, TypeScript build, Metro export, iOS/Android build or device auth/streaming test was run. This audit proves manifests/imports and official metadata, not functioning native binaries. No heavy test suite is warranted for this documentation-only edit.

Before claiming compatible: (a) render standalone + pnpm workspace fixtures with no local runtime link; install against public registry; (b) run Expo install checks/Doctor, typecheck, web export and native Metro bundles; (c) test neutral imports with React 18 and chosen SDK's React types without ambient DOM masking; (d) use Hermes development builds on iOS/Android for unary JSON/binary, abort, server stream incremental delivery/cancel and offline errors; (e) exercise real login/restore/refresh/expiry/logout and account-switch cache clearing; (f) verify optional peers do not pull browser SDK/DOM UI into mobile. Native builds and IdP integration are follow-up work, not evidence supplied by the release-target proposal.

Registry observations are time-sensitive; reproduce with GET `https://registry.npmjs.org/<package>` and inspect `dist-tags`, `versions`, `peerDependencies`, `peerDependenciesMeta`. SDK branch references can move; repository line evidence remains pinned to the stated HEAD.
